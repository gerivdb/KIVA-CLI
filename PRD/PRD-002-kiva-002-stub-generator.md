## Contexte et problème

Dans un workflow TDD autonome (No-HITL), les développeurs et agents écrivent d'abord les tests. Le problème actuel est que **la génération du code minimal (stubs, mocks, classes squelettes) reste entièrement manuelle**.

### État observé dans KIVA-CLI

- `kiva_cli/core/template_registry.py` + `ProjectManager` savent générer des **projets complets** à partir de templates (fastapi, react, go, rust).
- `ProjectManager.scaffold_element()` permet d'ajouter des services/components de manière très basique (juste des fichiers vides avec un commentaire).
- Il n'existe **aucun mécanisme** pour analyser un fichier de test (pytest, unittest, etc.) et en extraire automatiquement :
  - Les classes/fonctions à implémenter
  - Les signatures attendues
  - Les mocks nécessaires
  - Les retours minimaux pour faire passer le test (ou au moins le faire compiler)

Conséquence : après avoir rédigé un beau test (ou après un refactor de types via KIVA-004), le développeur/agent doit encore écrire manuellement le code "pour que le test passe". Cela ralentit fortement l'autonomie H0.

---

## Objectifs

**Objectif principal :**

> En tant qu'agent ou développeur KIVA, je veux un **Stub Generator** qui, à partir d'un ou plusieurs fichiers de test, génère automatiquement les stubs, interfaces, classes et mocks minimaux nécessaires pour que le test compile et passe (ou échoue de manière informative), en respectant les types canoniques définis dans `core/types.py`.

**Critères de succès mesurables :**

- [ ] Capable de générer des stubs Python (classes, fonctions, dataclasses, Enums) à partir de tests pytest
- [ ] Support des mocks pour les dépendances externes (subprocess, API, DB, skills)
- [ ] Génération de "minimal viable implementation" (retours par défaut, raise NotImplemented avec message clair)
- [ ] Utilise les types canoniques de PRD-KIVA-004 (ValidationState, LifecycleState, IntentHash, etc.)
- [ ] Intégration avec `TemplateRegistry` et `ProjectManager.scaffold_element`
- [ ] Génère des fichiers traçables (avec IntentHash dans un en-tête ou commentaire)
- [ ] Support initial pour Python + TypeScript (react) + Go (priorité écosystème)

## Périmètre

### In Scope ✅

- Nouvel agent / outil : `kiva_cli/generators/stub_generator.py` (ou `core/stub_generator.py`)
- Analyseur de test : parse pytest AST / unittest pour extraire signatures attendues
- Générateurs de code par langage :
  - Python (dataclass, Enum, class, function, async)
  - TypeScript (interface, type, class, mock)
  - Go (struct, interface, func)
- Système de "minimal implementation" (retour par défaut selon type de retour)
- Support des fixtures et dépendances (génération de mocks simples)
- CLI / commande : `kiva generate stubs --from-tests tests/test_foo.py --output src/`
- Intégration dans les pipelines (nouveau StepType ou skill)
- Tests du générateur lui-même

### Out of Scope ❌

- Génération de logique métier complète (ce n'est pas un "code generator" IA, c'est un **stub generator**)
- Génération de tests (inverse : ce sera peut-être un futur PRD)
- Support de tous les langages (priorité Python → TS → Go)
- Génération de tests pour le code généré (le Test-Repair Agent s'en chargera)

## Spécifications fonctionnelles

### 1. Commande principale

```bash
kiva generate stubs \
  --from-tests tests/test_project_manager.py \
  --language python \
  --output kiva_cli/core/generated/ \
  --use-canonical-types
```

### 2. Comportement attendu

Pour un test comme :

```python
def test_scaffold_project_creates_main_py():
    pm = ProjectManager()
    success, config, msg = pm.scaffold_project("demo", FrameworkType.FASTAPI)
    assert success is True
    assert (config.repo_path / "main.py").exists()
```

Le générateur doit produire quelque chose comme :

```python
# Generated by KIVA Stub Generator - IntentHash: 0x...
from dataclasses import dataclass
from pathlib import Path
from typing import Optional, Tuple, List
from kiva_cli.core.types import ValidationState, LifecycleState, FrameworkType, ProjectConfig

class ProjectManager:
    def scaffold_project(self, name: str, framework: FrameworkType, ...) -> Tuple[bool, Optional[ProjectConfig], str]:
        # TODO: minimal implementation
        return False, None, "Not implemented - generated stub"
```

### 3. Stratégies de génération

- `MinimalReturnStrategy` : retourne la valeur par défaut du type (None, [], "", 0, False, etc.)
- `RaiseNotImplementedStrategy` (par défaut pour les méthodes)
- `MockStrategy` pour les dépendances détectées
- `CanonicalTypeStrategy` : force l'utilisation des types de `core/types.py`

## Critères d'acceptation

```gherkin
Given un fichier de test pytest décrivant le comportement attendu d'une nouvelle classe
When on exécute le Stub Generator
Then il produit les fichiers .py avec les signatures exactes
And les imports utilisent les types canoniques de core/types.py
And les méthodes retournent des valeurs minimales ou lèvent NotImplemented avec un message clair
And le test compile (même s'il échoue encore sur la logique)

Given le générateur est invoqué depuis un pipeline
Then il écrit un IntentHash + phi_cps_delta dans le commentaire d'en-tête
And un événement WAL "stub_generated" est créé
```

## Architecture / Design

- Analyseur basé sur `ast` (Python) + tree-sitter ou regex pour les autres langages
- Templates Jinja2 ou string templates par langage
- Plugin system pour ajouter de nouvelles stratégies de génération
- Réutilisation de `Template` dataclass de `template_registry.py`

## Risques

| Risque | Probabilité | Impact | Mitigation |
|---|---|---|---|
| Stubs trop "vide" qui ne font pas avancer le test | Moyenne | Bas | Stratégie "raise + bon message" + documentation claire |
| Mauvaise inférence de signature sur tests complexes | Moyenne | Moyen | Mode "conservative" + review humaine optionnelle |
| Conflit avec le code existant | Basse | Moyen | Génération dans un dossier `generated/` + détection de conflit |
